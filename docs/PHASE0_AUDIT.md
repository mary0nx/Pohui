React 19, TypeScript strict, Vite 7, Tailwind 4, TanStack Query, React Router 7, Radix Dialog,
recharts, lucide. Разделы:
- **Главная** (`features/dashboard`): бюджет месяца с кольцом, доходы/расходы, быстрые действия,
  события, задачи на сегодня (с отметкой), покупки, семейная сводка, «живая» иллюстрация дома.

### Telegram
- Проверка initData: HMAC по токену бота, срок `auth_date` (24 ч), повторный вход тем же
  initData отзывает предыдущую сессию (`security/sessions.py`). Сессии: bearer-токен, в БД
  только SHA-256, скользящий срок 7 дней, абсолютный 30 дней.
- Бот: `/start`, команды, кнопки, вебхук с секретом (HMAC от `APP_SECRET_KEY`).
- Mini App SDK: BackButton, тема, CloudStorage (тема/палитра), безопасные области, вибро-отклик
  (только в Telegram 6.1+), добавление на экран «Домой» (8.0+).

### Фоновые задачи (`backend/app/workers`)
Цикл с advisory-lock и heartbeat-файлом: материализация регулярных платежей, планирование
напоминаний (события, задачи, личные, просроченные задачи, платежи, документы, утренние
списки покупок и задач в 09:00), рассылка outbox с повторами и backoff, очистка.
В production работает внутри web-процесса (`EMBEDDED_WORKER=true`).

### Семейная изоляция
Единый слой `visible()` / `get_visible()`; приватные записи видит только автор. Тесты с
«чужим» пользователем (`eve`) — в 14 тестовых файлах; e2e проверяет, что чужая семья не
открывает данные по прямой ссылке. В production проверено, что без сессии данные не отдаются;
проверка «чужой семьи с валидной сессией» в production не выполнялась (нужны два реальных
аккаунта) — покрыта тестами.

## 3. Состояние функциональности

### Работает и проверено
- Сайт на Pages, адрес API в сборке, CORS только для `my-family-app.pages.dev`.
- Backend на Render отвечает; PostgreSQL доступна; миграции на head.
- Вход через Telegram в настоящем клиенте iOS (скриншоты пользователя: семья, данные, профиль).
- Серверная проверка подписи initData, закрытый dev-вход, 401 без сессии, секрет вебхука.
- Бот отправляет сообщения (ключ Apple Pay доставлен в чат) и принимает `/start` (без него
  отправка в чат невозможна) — подтверждено косвенно.
- Календарь со сменами и праздниками в production (скриншот пользователя).
- Код: 125 backend + 65 frontend + 2 e2e тестов, линтеры и типы, CI зелёный.

### Реализовано, но не проверено в production
- **Доставка напоминаний** (outbox → Telegram) и утренние сводки 09:00: снаружи не видно,
  жив ли worker; бесплатный Render усыпляет сервис через ~15 мин без запросов, и тогда
  встроенный worker тоже спит.
- Тихие часы, настройки категорий уведомлений.
- Apple Pay от реальной оплаты iPhone (автоматизация настроена, первой оплаты ещё не было).
- Загрузка документов в production; кухня, «Вместе», импорт CSV в production.
- «Добавить на экран «Домой»» в реальном Telegram iOS.
- Приглашение второго участника в production.

### Реализовано частично
- **Документы**: хранилище `local` на диске Render — файлы пропадут при перезапуске или
  деплое (см. P0-2). Код S3-хранилища есть, не настроен.
- **AI**: код и тесты на сценарном провайдере есть; с реальной моделью не проверено, ключа нет.
- Переводы en/pl — только навигация и общие элементы.
- Повторяющиеся события: можно отменить одно повторение, но не изменить.
- Синхронизация — опрос каждые 5 с, без SSE/WebSocket.
- Банки: только Apple Pay и импорт CSV (push-уведомления банков iOS читать не даёт).
- «Живой дом»: есть только анимированная иллюстрация, без прогресса и данных.
- `TASKS.md` и `README.md` отстают от фактического состояния (нет смен, Apple Pay, редизайна).

### Отсутствует
- Механика «живой дом» (модель данных, правила, API, экран).
- Мониторинг доступности и ошибок, оповещения о падениях.
- Видимость worker снаружи (heartbeat не отражён в `/health/ready`).
- Автоматические резервные копии production-базы (на бесплатном Supabase своих бэкапов нет;
  скрипты бэкапа в репозитории рассчитаны на VPS).
- Экспорт данных семьи и удаление личного аккаунта пользователем.
- PostgreSQL Row-Level Security (дополнительный слой к `visible()`).
- Конвертация валют в сводках.

## 4. Блокирующие проблемы по приоритету

### P0 — надёжность и потеря данных
1. **Сервис засыпает, worker засыпает вместе с ним.** На бесплатном Render без входящих
   запросов процесс останавливается: напоминания и утренние сводки приходят с опозданием или
   не приходят, первое открытие приложения ждёт «пробуждения» до ~1 минуты.
   *Исправление:* внешний пинг `/health` каждые 10 минут (GitHub Actions по расписанию в этом
   репозитории — без секретов, или cron-job.org вручную) + видимость worker (пункт 3).
2. **Документы хранятся на эфемерном диске Render.** Любой деплой или перезапуск стирает
   загруженные файлы, а записи в БД остаются «битыми».
   *Исправление:* S3-совместимое хранилище Supabase Storage (бесплатно 1 ГБ) через уже
   существующий S3-адаптер; до настройки — блокировать загрузку в production с понятным
   сообщением, а не принимать файлы, которые пропадут.
3. **Нет способа узнать, работают ли фоновые задачи.** *Исправление:* `/health/ready`
   добавляет `worker: ok | stale | off` по возрасту heartbeat (без секретов и персональных
   данных); тест; тот же пинг из п. 1 будет его проверять.
4. **Ротация утёкших секретов (ручное действие).** Пароль базы и токен бота ранее попадали на
   скриншоты в переписке; ключ Apple Pay — тоже. Подтверждения, что они заменены, нет.

### P1 — эксплуатация
5. Резервные копии базы: ежедневный `pg_dump` (GitHub Actions по расписанию, зашифрованный
   артефакт с ограниченным сроком хранения; строка подключения — секрет репозитория).
6. Мониторинг ошибок: структурные логи уже есть; добавить оповещение о 5xx/падении
   (бесплатный uptime-монитор + ошибки worker в лог с понятным кодом).
7. HSTS на API, проверка CSP Pages для `connect-src`.
8. Актуализировать `TASKS.md`, `README.md`, `ARCHITECTURE.md` под фактическую схему
   (Render + Supabase + Pages, один процесс).

### P2 — качество
9. Срок жизни initData для входа: 24 ч → 1 ч (Mini App получает свежий initData при каждом
   открытии); сейчас перехваченный initData можно использовать сутки.
10. Размер главного JS (205 КБ gzip) — вынести форму операции и recharts в отдельные чанки.
11. Экспорт данных семьи и удаление аккаунта — до приглашения внешних пользователей.

## 5. План по этапам 0–7

Этапы 0–6 — из дорожной карты: инфраструктура и авторизация, семейное ядро, ежедневные функции,
живой дом, финансы и меню, AI и Telegram-бот, безопасность и эксплуатация. Этап 7 добавлен как
выпуск: бета для семьи и критерии «можно звать других». К следующему этапу переходим только
после выполнения критериев готовности предыдущего.

### Этап 0 — Инфраструктура и авторизация (закрывает P0)
- **Backend:** `app/db/health.py` + `app/main.py` — статус worker в `/health/ready`;
  `app/workers/loop.py` — heartbeat в памяти процесса (для режима одного процесса) и в файле;
  `app/integrations/storage.py` + `modules/documents` — блок загрузки при `storage=local` в
  production (503 `storage_not_configured`); S3 включается уже существующими настройками
  `STORAGE_BACKEND=s3`, `STORAGE_ENDPOINT`, `STORAGE_REGION`, `STORAGE_BUCKET`,
  `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY` (`app/config.py`).
- **Репозиторий:** `.github/workflows/keepalive.yml` — пинг `/health/ready` каждые 10 мин,
  падение workflow, если ответ не `ok` (это и есть простое оповещение по e-mail от GitHub).
- **Frontend:** `features/documents` — понятное сообщение, если хранилище не настроено.
- **Тесты:** readiness с живым/устаревшим heartbeat; запрет загрузки при local в production;
  загрузка через S3-адаптер (moto или локальный MinIO в CI).
- **Ручные действия:** Supabase → Storage → бакет и S3-ключи → Render → Environment;
  ротация пароля базы и токена бота (если ещё не сделано); новый ключ Apple Pay.
- **Риски:** лимит бесплатных часов Render (750 ч/мес — хватает на один сервис 24/7);
  GitHub отключает расписания через 60 дней без активности в репозитории.
- **Готово, когда:** `/health/ready` показывает `worker: ok` в течение суток подряд по логам
  keepalive; утреннее напоминание реально пришло в Telegram; загруженный документ переживает
  ручной Redeploy в Render; секреты заменены.

## 6. «Живой дом» — минимальная модель и правила

### Идея
Дом на главной — общий для семьи. Он растёт от реальных совместных дел: закрытых задач,
купленных списков, привычек, взносов в накопления, общих событий. Без соревнования между
участниками (как и общие очки задач сейчас), без наказаний: если семья давно ничего не
делала, дом выглядит «сонным», но ничего не теряет.

### Данные (одна миграция, 2 таблицы + 1 колонка)
```
house_progress                       -- состояние дома семьи (кеш)
  family_id     uuid PK → families
  xp            int  not null default 0
  level         int  not null default 1
  updated_at    timestamptz

house_events                         -- журнал начислений (источник правды)
  id            uuid PK
  family_id     uuid → families (index)
  kind          text  -- task_done | list_done | habit_checkin | goal_contribution | goal_reached | event_shared | streak_week
  source_type   text  -- 'task' | 'shopping_list' | 'habit_checkin' | 'savings_contribution' | ...
  source_id     uuid
  points        int
  actor_id      uuid null → users   -- для приватных записей не показывается
  created_at    timestamptz
  UNIQUE (kind, source_type, source_id)   -- одно действие = одно начисление

family_members.house_seen_level int default 1   -- какой уровень участник уже «отпраздновал»
```
Существующее переиспользуется: `tasks.points` (если задан — это очки задачи), `task_stats`
(недельные итоги), `habit_checkins`, `savings_contributions`, `shopping_items.status`,
`audit_log` не используется как источник (он для аудита).

### Правила начисления (константы в `modules/house/rules.py`)
| Действие | Очки | Ограничение |
|---|---|---|
| Задача выполнена | `tasks.points` или 10 | до 100 в день на семью |
| Список покупок закрыт (все куплено) | 15 | 1 раз на список в день |
| Отметка привычки | 5 | 1 раз на привычку в день |
| Взнос в накопления | 5 (не зависит от суммы) | до 3 в день |
| Цель накоплений достигнута | 50 | 1 раз на цель |
| Общее событие прошло с RSVP «иду» | 3 | — |
| Неделя активности (≥ 5 дней с действиями) | 30 | 1 раз в неделю |

- Отмена (задачу вернули в работу, товар «не куплен») удаляет запись журнала и вычитает очки.
- Уровни: порог уровня *n* = 50·n·(n+1) (100, 300, 600, 1000…), 10 уровней.
- Начисление — в той же транзакции, что и действие (`house.award(db, ctx, kind, source)` в
  `tasks/service.complete`, `shopping/service` и т. д.), идемпотентно по UNIQUE.
- Приватность: приватное действие даёт очки, но в ленте дома показывается без названия
  («кто-то закрыл личное дело»).

### Визуальные стадии (frontend, расширение `components/illustrations/Art.tsx`)
1 — участок и маленький дом, 2 — окна светятся, 3 — растение у двери, 4 — цветы на окнах,
5 — забор и дерево, 6 — второй этаж, 7 — сад, 8 — питомец, 9 — качели, 10 — фонари и сезонный
декор. Сезон (зима/весна/лето/осень) — по дате, без данных. Новый уровень — анимация
«распаковки» и конфетти один раз для каждого участника (`house_seen_level`).

### API
- `GET /api/v1/families/{id}/house` → `{level, xp, next_level_xp, stage_items[], recent: [{kind, points, at, actor?}]}`
- `POST /api/v1/families/{id}/house/seen` → отмечает просмотр нового уровня.
- Начисления только на сервере; клиент очки не присылает.

### Тесты
Идемпотентность (двойное выполнение задачи не даёт двойных очков), отмена, дневные лимиты,
изоляция семей, приватные записи без названий, пересчёт `house_progress` из журнала.
