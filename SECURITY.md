# Family OS — безопасность

## 1. Активы
* Личные и финансовые данные семьи, документы, приватные заметки.
* Токен Telegram-бота, ключ AI-провайдера, `APP_SECRET_KEY`, учётные данные БД и хранилища.
* Сессии пользователей.

## 2. Модель угроз

| # | Угроза | Мера защиты |
|---|--------|-------------|
| T1 | Подделка личности через initData | Проверка HMAC-SHA256 по официальной процедуре Telegram, `hmac.compare_digest`, проверка `auth_date` (по умолчанию не старше 24 ч, допуск часов 60 с). `initDataUnsafe` не используется сервером. Telegram ID из тела запроса не принимается. |
| T2 | Повторное использование перехваченного initData | TLS; ограниченный срок `auth_date`; повторный обмен того же initData отзывает ранее выданную по нему сессию; rate limit на `/auth/*`. |
| T3 | Кража сессии | Токен 256 бит, в БД только SHA-256 хеш; срок жизни (`SESSION_TTL_HOURS`), продление при активности, отзыв при выходе. Токен в `sessionStorage` (не cookie) — CSRF неприменим, т.к. браузер не прикладывает учётные данные автоматически. |
| T4 | IDOR / доступ к чужой семье | Все маршруты данных имеют вид `/families/{family_id}/…`; зависимость `get_family_context` проверяет членство; каждая выборка фильтрует по `family_id` и видимости; объект чужой семьи или чужой приватный объект → `404`. Интеграционные тесты на межсемейную изоляцию. |
| T5 | Утечка приватных записей партнёру | Единый фильтр видимости в списках, сводках, поиске, экспорте, истории изменений, AI-инструментах и уведомлениях. Тесты покрывают API и AI. |
| T6 | SQL injection | Только SQLAlchemy с параметрами, без конкатенации SQL; сортировка — по белому списку полей. |
| T7 | Prompt injection (текст пользователя, документы, описания операций) | Модель вызывает только инструменты из реестра; контекст семьи и пользователя берётся из сессии; аргументы валидируются; права проверяются в инструменте; изменения с последствиями — только через подтверждение человеком; данные из БД передаются модели как недоверенные. Нет инструментов SQL/shell/HTTP. |
| T8 | Злоупотребление AI (стоимость) | Дневные лимиты запросов и токенов на пользователя/семью, ограничение длины сообщения, таймауты, ограничение числа итераций tool calling. |
| T9 | Вредоносные файлы | Белый список типов по сигнатуре содержимого (PDF, JPEG, PNG, WebP, HEIC, TXT), лимит размера, имя файла в хранилище — случайный UUID, исходное имя санитизируется; отдача с `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`. |
| T10 | Публичный доступ к файлам | Нет постоянных публичных ссылок; скачивание по подписанному токену (HMAC, срок 5 мин, привязка к пользователю и документу) после проверки прав; S3 — presigned URL с коротким сроком. |
| T11 | Поддельные запросы на webhook бота | Секрет `TELEGRAM_WEBHOOK_SECRET` в заголовке `X-Telegram-Bot-Api-Secret-Token`. |
| T12 | Перебор/флуд | Rate limit (Redis, откат на память процесса) для auth, AI и общего API. |
| T13 | XSS | React экранирует вывод; `dangerouslySetInnerHTML` не используется; CSP в Caddy. |
| T14 | Утечка секретов | Секреты только в `.env` (в `.gitignore`); `.env.example` без значений; логи не содержат токенов, initData, текстов заметок и сообщений AI; ошибки Telegram/AI санитизируются. |
| T15 | Компрометация БД/Redis из сети | PostgreSQL и Redis не публикуются наружу (только внутренняя сеть compose). |
| T16 | Потеря данных | Ежедневный `pg_dump` + копия файлов, выгрузка вне сервера, скрипт проверки восстановления. |
| T17 | Dev-вход в production | При `APP_ENV=production` и `DEV_AUTH_ENABLED=true` приложение не стартует; маршрут dev-входа не регистрируется. |
| T18 | Повторное выполнение действия | Ключи идемпотентности для создания записей; AI-подтверждение — атомарный переход статуса; уникальные ограничения для фоновых операций. |

## 3. Авторизация
Проверки на каждом защищённом запросе: сессия → пользователь → членство в семье →
роль → принадлежность записи семье → видимость → допустимость действия.
Скрытие элементов интерфейса не является мерой безопасности.

Row-Level Security PostgreSQL в v1 **не включена**: авторизация реализована на уровне
приложения единым слоем и покрыта тестами. RLS рассматривается как дополнительный
слой в будущем (см. `TASKS.md`) и не заменяет проверки в коде.

## 4. Заголовки и транспорт
* HTTPS (Caddy, автоматические сертификаты Let's Encrypt), HSTS.
* CORS — только `CORS_ORIGINS` (в production — домен Mini App).
* `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`,
  разрешение встраивания (`frame-ancestors`) только для доменов Telegram Web.
* Ограничение размера тела запроса (API — 1 МБ, загрузка — `MAX_UPLOAD_MB`).

## 5. Журнал аудита
`audit_log` фиксирует значимые действия (создание/изменение/удаление, вход в семью,
приглашения, подтверждения AI) с кратким описанием без чувствительного содержимого.
Записи о приватных объектах видит только их автор.

## 6. Зависимости
Версии зафиксированы (`uv.lock`, `package-lock.json`). Проверка: `make audit`
(`pip-audit`, `npm audit`), в CI — на каждый push.

## 7. Сообщить о проблеме
Проект частный. Проблемы безопасности фиксируются в приватном трекере владельца.
